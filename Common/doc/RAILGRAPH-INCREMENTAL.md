# RailGraph 局部增量更新与已加载轨道复核

**[修改 · 2026-11-24 · STCS 4.3.4]** 正常的局部建图/每分钟复核默认不再输出控制台摘要。
`graph.log-successful-reviews: false` 为默认值，设为 `true` 可恢复成功摘要；修改后重启生效。
新增或变化的断轨、未知连接等路由问题仍输出警告（摘要最多列8项），同样的旧诊断不每分钟重复刷屏；扫描/复核异常仍照常记录。
有旧图覆盖的未加载诊断不算故障；检测周期、建图、图版本与行车保护不变。下方版本组合为原功能的历史基线。

版本组合：STA 2.4.0、STCS 4.3.0、SkyATO-Lite 0.2.0，配套 STF 4.1.1、SkyPCC 2.2.1。
STCS 拥有物理图、扫描结论和连通性解释；SAL 只消费 STA 的图及依赖校验结果，组织运营任务。

## 局部更新

- 注册、修改、删除 STCS 设备，只将设备前后位置及穿过该位置的旧边端点加入局部更新范围。
- STF 道岔、停车设备的注册目录每秒比较一次几何快照；只有目录变化才排队局部扫描，物理道岔开向变化不算拓扑修改。
- 轨道放置、拆除事件触发局部更新；周期复核补查其他插件或未被事件捕获的改变。
- 源扫描按批次启动，沿轨至下一个设备或未加载边界即停止；发现连接变化时只继续刷新受影响的相邻边界节点。
- 构建串行执行，重叠编辑合并排队，发布时原子合并已完成结果。导入设备服务不可用时保留旧图，不把不可用误认为空目录。
- 插入应答器会拆分经过其位置的旧边，包括两端未加载而设备位于已加载片段的情况；删除设备清除孤儿边，局部扫描重新连接邻接设备。

`/stcs rebuild`（`rescan` 同义）优先处理执行管理员附近的已加载源节点，然后处理其他已加载源。
控制台执行没有位置优先级。它不清空图，不加载区块，也不重扫未加载区域。
局部源每次仍受 `scan.max-distance-meters` 限制。未扫描部分与尚未完成的扫描不能覆盖为无连接。

## 卸载、未知与断轨

| 情况 | 处理 |
| --- | --- |
| 以前确认的边，本次扫描到未加载边界 | 保留旧连接及几何，继续可用于静态规划 |
| 没有历史连接的未加载方向 | 仍未知，不能凭空生成边 |
| 已加载区域确认缺轨或几何不连通 | 删除本次已证实不存在的连接，或将保留边标记为 rail_broken |
| 已确认断轨的区域后来卸载 | 继续保留故障，不能因为卸载而转为连通 |
| 修复后的完整物理扫描成功 | 更新连接并清除相应旧断轨观测 |

已知特定端口可以由旧的出边或入边覆盖。整个源节点无法检查（端口 none）时，需要既有完整端口覆盖，
不把残缺旧图中的未知方向转换为连通。调度失败等其他异常继续作为阻塞原因。

保留拓扑不证明占用空闲、道岔开向正确或 MA 有效；运行仍由 STCS 发放许可、STF 执行与监督。
外部替换地图或离线编辑后，应在相关区域加载后明确重扫，不能把历史连接当作新地图的证据。

## 周期复核与线程

STCS/config.yml：

```yaml
graph:
  review-interval-seconds: 60
  sources-per-tick: 4
```

检查周期为现实时间秒数，范围 1–86400；每批启动源扫描或区块复核的数量范围 1–64。
统一周期由 STCS 调度，物理读取仍派发到各区块所属的 Folia 区域线程；检查前及执行时都确认区块已加载。
周期复核按旧边的轨道位置分区块检查，即使端点卸载，也可以检查中间已加载片段。未加载片段跳过，不主动加载。
同时复核轨道存在及方向几何；登记道岔的拓扑端口与实时选定开向分别处理。
仍有真实未解决问题的已加载源会进入局部重试，支持断轨修复后的重新发现。

旧配置 `scan.only-loaded-chunks: false` 不再允许拓扑维护加载区块，启动时迁移为 true；新配置键会补入现有文件。
一分钟是后台检查周期，不是瞬时故障检测保证；实际行车保护与物理检查继续保留。

## 版本与 STA 契约

健康扫描没有改变几何、设备定义或阻塞结论时，不发布新结构版本。`lastCheckedMillis` 单独记录检查时间。
全局图 revision 仍用于一致性与 MA 围栏；真实结构或阻塞结论变化才发布新快照。

保持 graph JSON schemaVersion=3，新增以下可选字段（语义能力版本为 1）：

- `topologySemantics: 1`
- `routingIssues`：由 STCS 解释后、实际阻塞路径规划的问题。
- `scanDiagnostics`：最近建图的检查诊断，可能包含不阻断已有连接的卸载记录。
- `lastCheckedMillis`：最近一次建图/周期检查完成时间，不能用作 MA 或占用证据。

原 `unresolved` 仍作为图快照诊断保留。消费者不能再仅根据它包含 chunk_not_loaded 就推断断路。

STA 的 RailNetworkService 增加默认方法：

```java
TopologyDependency captureDependencies(long revision, List<String> edgeIds);
TopologyDependency.Check checkDependencies(TopologyDependency dependency);
```

DTO 位于 api.v9，version=9，保存不可变的边 ID→不透明拓扑摘要。摘要包含边几何、端点拓扑、比例与相关阻塞结论，
不包含检查时间或实时道岔开向。捕获要求计划的精确快照版本；版本竞争、未知边或不支持的提供者返回不可用。
检查结果为 UNCHANGED、CHANGED 或 UNAVAILABLE，并返回被改变/移除的依赖边。
默认方法保留原接口的进程内兼容性，SAL 0.2.0 的发布和运行依赖新 STCS 提供这些能力。

## SAL 行为与升级

SAL 的 station/depot/property/message 位置只从已登记 RailGraph 的轨道柱中绑定，不独立扫描物理铁轨。
未建图的新轨道需先完成 STCS 设备登记或局部重扫。牌子格式、运营线路名称与停站规则不变。
SAL 使用 routingIssues，不自行把卸载诊断解释为断路。

发布时保存全线路依赖；图更新后先检查摘要，无关变化只推进所见版本，保留发布状态。
受影响的已发布线路自动重新验证；成功后更新依赖，失败则取消发布。运行任务还记录当前出库/行驶/回库路径的依赖；
实际依赖改变时保持并进入 RECOVERY_REQUIRED，管理员检查后可 resume 先回库，不让旧路径继续自动执行。
旧发布记录首次使用时补建依赖；服务器重启后的旧任务仍遵循既有恢复规则。

全局 MA 版本校验不取消：结构变化时车端需要当前版本许可，不能为了保持线路发布而复用旧 MA。
“无关线路无需重发”不等于“旧许可跨版本继续有效”。保留地图、配置、列车、轨道图和全部占用账本，配套替换后完整重启。
